# Attachments and Pasted Images
Status: Approved for build
Date: 2026-10-25

**Builds on the implemented code and on `docs/specs/ticket-discussion.md`, `docs/specs/username-login.md` and `docs/specs/ticket-history.md` (read-only references; this spec edits none of them).** Terminology follows the MVP ("work item"; the table and API may still be called `issues`). Acceptance criteria are numbered from 1 within this spec; references to other specs are written "Discussion AC n", "Login AC n", "History AC n".

It reuses: `req.user` (Login), `loadIssue` and the archived-project guard in `server/routes/guards.js`, `deleteIssue` in `server/data/issues.js` (one `db.transaction`), the history recorder in `server/data/history.js`, `COMMENT_MAX_LENGTH` (2000) in `server/validation.js`, the Discussion box and `<dialog id="detail">` in `public/js/board.js` / `public/board.html`. Today the description is a plain `<textarea>`, and comment bodies are rendered with `textContent` (never parsed as HTML); that safety property must survive this feature.

## Problem

Work items carry only text. Users cannot attach a spec, log or spreadsheet to a work item, and cannot paste a screen snapshot into a bug report or a comment, which is the most common way a defect is described. The owner wants both, built on one file-storage layer that stays on local disk for the POC but can be swapped by the BOE later without touching the rest of the app.

## User stories

1. As a user, I attach one or more files to a work item and see them listed with name, size, uploader and time.
2. As a user, I download any attachment, and preview image attachments in the browser without downloading.
3. As a user, I paste a screenshot (Ctrl/Cmd+V) into the Discussion box and, after I post, the image shows inline in the comment.
4. As a user, I paste a screenshot into the description box and see it inline in the description.
5. As a user, I remove an attachment I uploaded; other people cannot remove it.
6. As a user, I see in History who added or removed which attachment.
7. As the owner, I can later replace local-disk storage with BOE storage by changing one module.
8. As the owner, deleting a work item leaves no orphaned files on disk.

## Decisions (confirmed by the owner; the developer does not need to ask)

- Pasted images ARE attachments. A paste uploads the image through the same endpoint and storage as a file attachment, so there is one code path, one size limit and one set of rules. Pasted images also appear in the Attachments list.
- Inline images are referenced from text by a short token, `![image](attachment:<id>)`, written into the textarea at the cursor when the paste upload succeeds. The text stays plain text in the database.
- Pasting and attaching require a saved work item (an id). In the Create dialog the Attachments control and paste handler show "Save the work item first." and do nothing.
- Uploads are sent as the raw request body (not multipart), so no new dependency is needed.

## Acceptance criteria

### Storage layer

1. A new module `server/data/storage.js` is the only place that touches the file system for attachment bytes. It exports exactly: `put(stream_or_buffer) -> Promise<{ key, size }>`, `open(key) -> readable stream` (throws a not-found error if missing), `remove(key) -> Promise<void>` (no error if already missing) and `exists(key)`. Nothing else in `server/`, `public/` or `tests/` (other than `tests/storage.test.js`) imports `fs` for attachment files; a source test in `tests/source.test.js` fails if it does.
2. The storage `key` is generated by the server (random, unguessable, no user input, no extension) and the file is stored at `data/files/<key>` under the repo root. The original filename is stored only in the database, never used as a path. A filename such as `../../etc/passwd` is saved and served as a harmless display name, and nothing is written outside `data/files/`.
3. `data/files/` is git-ignored (`git check-ignore data/files/x` succeeds, and the existing `/data/` rule must not be loosened or accidentally hide `server/data/`; `git check-ignore server/data/storage.js` must fail). The directory is created on start if missing.
4. A test swaps `storage.js` for an in-memory fake (same four functions) and the upload, download and delete flows still pass. This proves nothing outside the module depends on disk layout.
5. All SQL for attachments lives in `server/data/attachments.js`; routes call it and `storage.js` and contain no SQL.

### Limits and allowed types

6. Maximum file size is 10 MB (10,485,760 bytes) per file, enforced while streaming, so an oversized upload is rejected without being fully stored. Rejection returns 413 with `File is too large (max 10 MB).` and leaves no file on disk and no database row. The limit is one constant in the attachment-types list (see 7), not repeated elsewhere.
7. Allowed types are one single-source list in `server/attachmentTypes.js` (same style as `statuses.js`), each entry `{ extension, mime, inline }`. Initial list: images `png`, `jpg`/`jpeg`, `gif`, `webp` (`inline: true`); documents `pdf`, `txt`, `md`, `csv`, `log`, `docx`, `xlsx`, `pptx`, `zip`. SVG, HTML, JavaScript and executables are not allowed. A disallowed extension returns 415 with `That file type is not allowed.` and stores nothing.
8. For `inline: true` types the server checks the first bytes against the type's signature (PNG, JPEG, GIF, WebP). A `.png` whose bytes are not a PNG returns 415 and stores nothing.
9. A work item holds at most 25 attachments. The 26th returns 409 with `This work item already has 25 attachments.` The count is one constant.
10. A zero-byte upload returns 400 with `File is empty.`
11. Hard-coded type names appear only in `server/attachmentTypes.js`; `GET /api/attachment-types` returns the list and limits so the client does not hard-code them.

### Attachments API

12. `POST /api/issues/:id/attachments` with the file bytes as the body, `Content-Type` the file's MIME type and the filename in a URL-encoded `X-Filename` header, creates an attachment and returns 201 `{ id, issue_id, filename, mime_type, size_bytes, uploader_id, uploader_name, created_at, inline }`. The uploader is `req.user`; the client cannot supply it. Unknown work item returns 404 `Work item not found.`; no session returns 401 (Login AC).
13. `GET /api/issues/:id/attachments` returns the list, newest first, readable on archived projects.
14. `GET /api/attachments/:id/download` streams the bytes with `Content-Disposition: attachment; filename*=UTF-8''<name>`, the stored MIME type, and `X-Content-Type-Options: nosniff`. Unknown id returns 404 `Attachment not found.` Readable on archived projects.
15. `GET /api/attachments/:id/preview` works only for `inline: true` types: it streams with `Content-Disposition: inline` and `nosniff`. For any other type it returns 415. It requires a session like every `/api` route.
16. `DELETE /api/attachments/:id` returns 204 and removes the database row and the file. Only the uploader may delete (see Permissions). Unknown id returns 404.
17. Upload and delete on a work item of an archived project return 409 with the existing archived message (`This project is archived; its work items are read-only.`), checked after 404 and 403, matching Discussion AC order.
18. If the database insert fails after the file was stored, the file is removed (no orphan). If `remove` fails after the row is deleted, the error is logged and the request still succeeds.

### Permissions

19. Any signed-in user can add attachments to, list, preview and download from any work item they can see (there are no per-project permissions yet).
20. Only the user who uploaded an attachment (`uploader_id` equals `req.user.id`) can delete it. Anyone else gets 403 with `You can only delete your own attachments.` and the file remains. This mirrors comments (Discussion/Login: author only). The Delete button is shown only to the uploader, but the server enforces the rule regardless.

### Deleting a work item

21. Deleting a work item (the existing delete flow) deletes all its attachment rows in the same transaction as the item, comments and history, and then removes every one of its files from storage. After deletion, `data/files/` contains none of those keys, and `GET /api/attachments/:id/download` for them returns 404. A failure to remove one file is logged and does not stop the others or fail the delete.
22. Deleting a work item that has no attachments behaves as before.

### Attachments UI

23. The work item detail dialog (saved items only) has an Attachments section with heading `Attachments (n)`, an "Add files" control (also accepts several files at once and drag-and-drop onto the section), and a list row per attachment: filename, human size (for example `2.3 MB`), uploader name, relative time (`timeFormat`), a Download link, and a Delete button for the uploader only.
24. Image attachments show a small thumbnail (from `/preview`); clicking it opens the full image in a new browser tab. Non-image rows show no thumbnail.
25. While a file uploads the row shows "Uploading..."; on a rejected file the section shows the server's message (too large, type not allowed, limit reached) and the other selected files still upload.
26. Delete asks for confirmation, then removes the row without reloading the page, and the heading count updates.
27. On an archived project the Add control and Delete buttons are hidden; the list, download and preview still work.
28. In the Create dialog (no id yet) the Attachments section shows "Save the work item first." and has no upload control.
29. File names are always inserted with `textContent` (never `innerHTML`). A file named `<img src=x onerror=alert(1)>.png` displays as literal text and runs nothing.

### Pasted images

30. Pasting an image from the clipboard (a `paste` event whose clipboard has an `image/*` file, for example a screenshot) into the Discussion textarea or the description textarea of a saved work item uploads it as an attachment named `pasted-image-<YYYYMMDD-HHMMSS>.png` (or the clipboard's real extension), subject to ACs 6 to 11, and inserts `![image](attachment:<id>)` at the cursor. The default paste does not also insert text. Pasting plain text behaves as today.
31. While the paste upload runs, the Post button (comments) or Save button (description) is disabled and a "Uploading image..." note is shown; on failure the server message is shown, nothing is inserted, and the existing text is kept.
32. A comment body or description may contain several tokens. The token counts toward the 2000-character comment limit; the description has no new limit.
33. After a comment is posted, each valid token renders as an inline `<img>` (max width 100% of the comment, max height 400 px) at the token's position within the surrounding text; the surrounding text still renders with `textContent` semantics and line breaks as today. Clicking the image opens `/preview` in a new tab.
34. The description is rendered, in the dialog's read view, by the same renderer: plain text with tokens replaced by images. The edit view stays a plain `<textarea>` showing the raw token text. Below the textarea (while editing) a small "Images in this description" strip shows thumbnails of the tokens present, so the author can see the paste worked. No Markdown, no bold, no links: tokens are the only markup.
35. A token renders as an image only if the attachment exists, belongs to the same work item, and is an `inline` type. Otherwise it shows as the literal text `[image removed]` (deleted or unknown id) or as the unchanged raw text (belongs to another work item). A token can never make the page load an arbitrary URL: the `src` is always `/api/attachments/<id>/preview` built by the client from the numeric id.
36. The renderer is one shared function in `public/js/` (for example `richText.js`) used by both comments and the description, with a Node unit test that covers: no token, one token, several tokens, adjacent tokens, a token with a non-numeric id (stays literal text), text containing `<script>` (stays literal text), and a removed attachment.
37. Deleting an attachment that is referenced in a comment or the description leaves the text unchanged and the image position shows `[image removed]` after the next load of that item.
38. Editing a comment (Discussion/Login author-only edit) keeps tokens as editable text; pasting into the edit box also works under the same rules.

### History

39. Adding an attachment (file or pasted image) writes a history entry in the same transaction as the attachment row, with the actor taken from `req.user` (id and name snapshot), shown in the History tab as `<Actor> added attachment <filename>`.
40. Removing an attachment writes an entry in the same transaction as the row delete, with the actor from `req.user` (the deleter), shown as `<Actor> removed attachment <filename>`. The filename is the stored display name at the time, so the entry stays readable after the file is gone.
41. Deleting the whole work item removes its history with it (History decision), so no attachment entries remain for a deleted item. Uploads rejected by AC 6 to 10 write no history.
42. History order and API shape stay as in History AC 15 (`changes` entries with `field: 'attachment'`, `old` null and `new` the filename for added, the reverse for removed). The `attachment` entry is added to `server/historyFields.js`; `tests/history.test.js` continues to pass.

### Extensibility and regression

43. `npm test` passes with the existing tests plus new ones for: storage (`tests/storage.test.js`), attachments API (`tests/attachments.test.js`) covering ACs 6 to 22 and 39 to 41, and the renderer (AC 36).
44. Existing behaviour is unchanged: creating, editing, moving and deleting work items; comments; history; login. Existing databases gain the new table on start with no manual step and no data loss.

## Data model changes

One new table in `server/db.js` (`CREATE TABLE IF NOT EXISTS`, so existing databases gain it on start; no migration, no backfill):

- **attachments**: `id` INTEGER PK, `issue_id` INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE, `storage_key` TEXT NOT NULL UNIQUE, `filename` TEXT NOT NULL (display name only, sanitized: path separators and control characters removed, max 200 chars), `mime_type` TEXT NOT NULL, `size_bytes` INTEGER NOT NULL, `uploader_id` INTEGER NULL REFERENCES users(id), `uploader_name` TEXT NOT NULL (snapshot, like comments and history), `created_at` TEXT NOT NULL (ISO, same format as `comments.created_at`). Index on `(issue_id, id)`. No CHECK constraints on type.

`comments` and `issues` gain no columns; inline images are referenced by token inside the existing `body` and `description` text.

New single-source file `server/attachmentTypes.js` (allowed types, size limit, per-item count limit). New row in `server/historyFields.js` for `attachment`. Files live on disk at `data/files/<storage_key>` (git-ignored through the existing `/data/` rule).

## Out of scope

- Authentication changes, permission groups, project-level permissions (delete rule is uploader-only until those exist).
- Rich text or Markdown beyond the single image token; links, bold, lists.
- Image editing, resizing, cropping, annotation, video, and drag-dropping images onto the textarea (paste only; drag-drop is for the Attachments section).
- Virus scanning, thumbnails generated server-side, EXIF stripping, deduplication, versioning, replacing a file.
- Quotas per project or per user; total storage reporting.
- A background sweep for orphan files (for example from an abandoned pasted image or a crash between file write and database insert).
- Attachments on projects or comments as separate objects (comments only reference item attachments by token).
- Copying attachments when a work item is cloned (no clone feature exists).
- Real BOE storage backend; only the swappable module boundary.
- Pasting in the Create dialog before the item is saved.

## Decisions confirmed by the owner (2026-10-25)

All PM recommendations were accepted:

- Delete: uploader only, until permission groups exist.
- Limits and types: 10 MB per file, 25 files per item, the allowed list in AC 7, no SVG.
- No paste or attach in the Create dialog; the item must be saved first.
- Deleting a comment leaves its pasted images in the Attachments list; they go with the work item or their uploader.
- Pasted images appear in the Attachments list and get history entries like any attachment.
- Description rendering: plain text with the image token as the only markup (AC 34); no Markdown.
- Download always saves; clicking a thumbnail previews.
- Preview and download require login, so images in comments load only while signed in.

## Open questions

None blocking. Known unknown: the BOE storage target (file share, S3-compatible, database BLOB) is not yet known. The owner did not answer. Do not guess: `server/data/storage.js` and its four-function streaming interface (AC 1) are the swap point, and nothing outside it may depend on disk layout (AC 4).

## Implementation notes for the developer

Suggested order, running `npm test` after each step:

1. `server/attachmentTypes.js`, then `server/data/storage.js` and `tests/storage.test.js` (including the traversal-filename case and the fake-swap test, AC 4). Use `fs.createWriteStream` with a counter that aborts and unlinks at 10 MB; write to a temp name in `data/files/` and rename on success.
2. `server/db.js`: the `attachments` table. `server/data/attachments.js`: `addAttachment`, `listAttachments`, `getAttachment`, `deleteAttachment`, `countAttachments`, `listKeysForIssue`. Add/delete take the same `db` and call `history` inside the caller's transaction (AC 39, 40). Add the `attachment` entry to `server/historyFields.js` and check `tests/history.test.js` and `public/js/historyFormat.js` render `added attachment` / `removed attachment` (the generic old/new rendering may need a small case for a field whose old or new side is empty).
3. `server/routes/attachments.js`, mounted in `server/app.js`. Upload route uses `express.raw`-style streaming, not `express.json` (the global `/api` JSON parser ignores other content types, but check it does not buffer them); the 413 must be produced from the stream counter, not from a body-parser default. Reuse `loadIssue`, the archived guard, and the 404 then 403 then 409 order; put the uploader check in `routes/guards.js` next to the comment author check.
4. `server/data/issues.js` `deleteIssue`: collect the storage keys inside the transaction, delete rows, and call `storage.remove` for each key after the transaction commits (best effort, log failures). Check whether any project-delete path exists and, if so, do the same.
5. `public/js/richText.js` (shared renderer, AC 36, with a Node test like `tests/historyFormat.test.js`), then the Attachments section and paste handler in `public/js/board.js` / `public/board.html` / `public/css/app.css`; wire the renderer into `renderComment` (currently `el('div', { class: 'message-body' }, comment.body)`) and the description read view.
6. `tests/source.test.js`: add the "only `storage.js` uses `fs` for attachment bytes" and "no SQL outside `server/data/`" checks. `README.md`: mention the files directory and limits. Do not commit `data/files/`.
