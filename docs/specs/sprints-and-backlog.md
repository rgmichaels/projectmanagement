# Sprints and Backlog
Status: Approved (owner-reviewed)
Date: 2026-10-26

**Builds on the implemented code and on `docs/specs/board-mvp.md`, `docs/specs/permission-groups.md`, `docs/specs/ticket-history.md` and `docs/specs/epic-view.md` (read-only references; this spec edits none of them).** Terminology follows the MVP ("work item"; the table and API still say `issues`). Acceptance criteria are numbered from 1 within this spec; references to other specs are written "MVP AC n", "History AC n".

It reuses: the single-source list style of `server/statuses.js` (`STATUSES`, `isTerminalStatus`) and `server/types.js` (`isEpic` flag, `isEpicType`); `assertCan`, `loadProject`, `assertWritable`, `actorFrom` in `server/routes/guards.js`; the `write` permission in `server/groups.js`; `checkIssueFields` in `server/validation.js`; `updateIssue`, `createIssue`, `bottomRank`, `rebalanceIfNeeded` in `server/data/issues.js`; `recordChanges` and `HISTORY_FIELDS` in `server/data/history.js` / `server/historyFields.js` (the model for the sprint audit log); the additive-migration pattern in `server/db.js`; the read-only lists served by `server/routes/meta.js`.

## Problem

Every work item in a project is on the board all the time. There is no place to hold work that is not yet planned, and no way to commit to a slice of work for a time-box. The owner wants the Jira planning loop: a **Backlog** page per project with an ordered list of unscheduled work and sprint sections, sprints that are created, started and completed, and a board that shows only the work in the current sprint.

## User stories

1. As a user, I open a project's Backlog page and see sprints (active first, then planned) and, below them, the backlog: work items not in any sprint, in priority order.
2. As a user, I reorder the backlog and the items inside a sprint by dragging.
3. As a user, I type a title in a quick-create row at the bottom of the backlog (or of a sprint) and the item is created there.
4. As a user, I create a sprint with a name, and optionally a goal and start and end dates, and rename or edit it later.
5. As a user, I start a planned sprint, so its items appear on the board.
6. As a user, I complete the active sprint and choose, in one step, whether its unfinished items go to the backlog, to the next planned sprint, or to a new sprint created on the spot.
7. As a user, I move an item between the backlog and a sprint by dragging it on the Backlog page or by using a Sprint control in the work item dialog.
8. As a user, I see on the board only the active sprint's items, and a clear message when there is no active sprint. I can still create work items from the board; with no active sprint they go to the backlog and the board says so.
9. As a user, I see each sprint change in the work item's History.
10. As a Viewer, I can read the Backlog page but change nothing; on an archived project nobody can change anything.
11. As the owner, adding a status to `server/statuses.js`, a sprint state to its list or a sprint event kind to its list needs no other change.
12. As a user, I see who created, edited, started, completed or deleted a sprint, and when, in a Sprint history view on the Backlog page.
13. As a user, I am warned (on the board and on the Backlog page) when the active sprint's end date has passed.
14. As a user, epics stay out of sprints (as in Jira) but I can still find, open and group by them.

## Decisions (owner-approved 2026-10-26)

Decisions 1-11 were proposed in the draft and stand unless amended below. Decisions 12-20 record the owner's answers to the draft's open questions.

1. **One active sprint per project.** Enforced by the server (and by a unique index), not only by the UI. Starting a sprint while another is active is refused with 409.
2. **Sprint states** are a single-source list in a new file `server/sprintStates.js` (`Planned` initial, `Active`, `Completed` final), the same style as `statuses.js`. No sprint state name is written anywhere else in `server/` or `public/js/`.
3. **Work item statuses are unchanged.** A sprint does not own a status. "Unfinished" means the item's status is not the terminal status (`isTerminalStatus`); resolution is not considered (same rule as Epic View Decision 5). Unfinished items keep their status when they move.
4. **Membership is one nullable column.** A non-epic item is in at most one sprint (`issues.sprint_id`); `null` means backlog. Done items stay in their completed sprint as a record.
5. **Ordering uses its own column, `issues.sprint_rank`**, the position inside the item's container (a sprint or the backlog). The existing `rank` keeps meaning "position in a board column" and is not touched, so reordering on the board and on the Backlog page cannot disturb each other.
6. **Archived projects:** the Backlog page, sprint data and sprint history are readable; every sprint or backlog write returns 409 (`assertWritable`), like work items.
7. **Sprint dates are display-only**, with one exception (Decision 19, the overdue warning). Starting and completing a sprint is always a manual action; reaching the end date does nothing automatically.
8. **Epic membership (`epic_id`) is independent of sprint membership** and unaffected by this spec. The Epic View lists all children regardless of sprint.
9. **Where new items land.** The API default for a new item is the backlog, at the bottom. The board's create dialog and the Epic View "Create child" send the active sprint id when there is one (so what you create from the board shows on the board), and the backlog otherwise (Decision 17).
10. **Migration of existing databases (owner chose option A).** For each project that already has non-epic work items, create one sprint named `Sprint 1` containing all of the project's existing non-epic items. It is `Active` for a non-archived project and `Completed` for an archived project. The backlog starts empty and the board looks the same after the upgrade, except that epics are no longer drawn as cards (Decision 16). Projects with no non-epic items get no sprint. A new project starts with no sprint and an empty backlog.
11. **One shared overdue rule** (Decision 19) so the board and the Backlog page cannot disagree.
12. **Permission:** all sprint and backlog changes need the existing `write` permission (every group except Viewer, today Admin and Member). Viewers read only. No new permission is added. (Owner decision.)
13. **Terminal-status items stay in the completed sprint,** whatever their resolution (Done, Won't Do style values all count as finished). (Owner decision.)
14. **Complete-sprint dispositions.** `backlog`, `next-sprint` (a Planned sprint of the project) or `new-sprint` (a sprint created in the same transaction, name defaulted to the next number, editable). The dialog offers `new-sprint` always, so it is available when no planned sprint exists. (Owner decision; always offering it is a superset of the owner's wording.)
15. **New backlog items go to the bottom** of the backlog (and of a sprint). (Owner decision.)
16. **Epics are excluded from sprints, as in Jira.** An epic (any type with the `isEpic` flag in `server/types.js`) cannot be assigned a sprint, is never shown in a sprint section, never counts in a sprint's item or done counts, and never appears as a card in a board column. The API returns 400 if `sprint_id` (or `sprint_rank`) is set on an epic. Epics have `sprint_id` and `sprint_rank` null. Where epics remain visible is fixed by AC 29 and AC 31. (Owner decision; the visibility rules are the product manager's.)
17. **Create from the board with no active sprint** creates into the backlog, and the create dialog says so ("No sprint is active. This work item will be created in the Backlog."). The create control stays visible. (Owner decision.)
18. **Sprint audit log now.** A sprint-level event log records created, edited, started, completed (with disposition and counts) and deleted, with actor and time, in new tables; it is readable by API and shown in a "Sprint history" view on the Backlog page. It follows work item history: a single-source list in `server/sprintEvents.js` (event kinds and tracked sprint fields, like `HISTORY_FIELDS`), a data file `server/data/sprintHistory.js` called from inside the writing transaction, and a read-only route. (Owner decision.)
19. **Overdue warning.** An Active sprint is *overdue* when it has an `end_date` and today's date (the viewer's local calendar date) is after it; the end date itself is not overdue. The board and the Backlog page show a visible banner or badge with text (not colour alone). Nothing else about dates is enforced. (Owner decision.)
20. **Epics on the Backlog page.** Because epics have no sprint, the Backlog page gets a small read-only "Epics" section (AC 31) so they can be found and opened. This is the one addition beyond the owner's answers; it replaces the draft's "epics panel" out-of-scope line, and is listed in Open questions for the owner to veto.

## Acceptance criteria

### Data and migration

1. A table `sprints` exists with `id, project_id, name, goal, start_date, end_date, state, created_at, started_at, completed_at`. `state` is one of the values in `server/sprintStates.js`; there is no CHECK constraint (like statuses). `start_date` and `end_date` are `YYYY-MM-DD` or null; `goal` defaults to the empty string.
2. `issues` gains `sprint_id` (nullable, references `sprints`) and `sprint_rank` (integer; set for every non-epic item once assigned, null for epics). A work item with `sprint_id` null is "in the backlog" (epics are in no container at all).
3. A unique index permits at most one sprint per project whose state is the active state. The state name comes from `server/sprintStates.js`.
4. On start of an existing database that lacks `issues.sprint_id`, the migration (idempotent; runs once) adds the columns and tables, then applies Decision 10: per project with at least one non-epic work item, one `Sprint 1` holding every non-epic item, `sprint_rank` set from the current `rank` order in steps of 1000, state Active (project not archived) or Completed (project archived, `started_at` and `completed_at` set to the migration time). Existing epics keep `sprint_id` and `sprint_rank` null (they stay out of Sprint 1). A project whose only items are epics gets no sprint. No work item history is backfilled, no sprint events are backfilled, and no `updated_at` changes.
5. Running the migration twice, or opening a fresh database, creates no extra sprints. A fresh database has no sprints.
6. After migration, the board of a non-archived project with items shows the same non-epic items in the same columns and order as before, and shows the same epic swimlanes (visual check by QA on a copy of a real database). The only visible difference is that epic-type items are no longer drawn as cards (AC 24).

### Sprint endpoints

7. `GET /api/projects/:id/sprints` returns 200 with every sprint of the project, each with `item_count` and `done_count` (non-epic items, and non-epic items in the terminal status). Order: the active sprint first, then planned sprints by id, then completed sprints newest `completed_at` first. Unknown project returns 404. Signed-out returns 401. Readable on archived projects.
8. `POST /api/projects/:id/sprints` with `{ name, goal?, start_date?, end_date? }` creates a sprint in the initial state and returns 201. `name` is required, trimmed, 1-80 characters. `goal` is optional text up to 500 characters. Dates must be valid `YYYY-MM-DD` or null/omitted; if both are given `end_date` must not be before `start_date`. Violations return 400 with an `error` message. Requires `write` (403 for Viewer, checked before the project is loaded), project exists (404), project not archived (409), then validation (400). Records a `created` sprint event (AC 41-42).
9. `PATCH /api/sprints/:id` edits `name`, `goal`, `start_date`, `end_date` of a Planned or Active sprint with the same validation as AC 8. State cannot be changed through PATCH (the field is ignored or rejected with 400). A Completed sprint returns 409. Same guard order and archived rule as AC 8. Records one `edited` sprint event with a change row per field whose value changed; no event when nothing changed.
10. `DELETE /api/sprints/:id` is allowed only for a Planned sprint (409 otherwise). Its items return to the backlog, keeping their relative order, placed at the bottom of the backlog; each of them gets a sprint change in work item History (AC 39). Returns 204. Same guard order as AC 8. Records a `deleted` sprint event with the sprint's name snapshot and the number of items returned; the event outlives the sprint.
11. `POST /api/sprints/:id/start` moves a Planned sprint to Active and sets `started_at`. If the project already has an active sprint it returns 409 (`Complete the active sprint first.`). Starting a sprint with no items is allowed. A sprint that is not Planned returns 409. Same guard order as AC 8. Records a `started` sprint event.
12. `POST /api/sprints/:id/complete` requires the sprint to be Active (409 otherwise) and a body `{ disposition: 'backlog' | 'next-sprint' | 'new-sprint', next_sprint_id?, new_sprint_name? }`. A missing or other `disposition` returns 400. With `next-sprint`, `next_sprint_id` must be a Planned sprint of the same project, otherwise 400. With `new-sprint`, `new_sprint_name` is optional (trimmed, 1-80 characters, 400 otherwise); when omitted or blank the server uses the default name (AC 16). It runs in one transaction: the sprint becomes Completed with `completed_at`; with `new-sprint` a new Planned sprint is created (and gets its own `created` event); every non-epic item of the sprint not in the terminal status moves to the backlog (top, relative order kept), to the chosen sprint (bottom, relative order kept) or to the new sprint (relative order kept); items in the terminal status stay in the completed sprint. If any step fails nothing changes, including the audit events.
13. The complete response is 200 with `{ sprint, moved: { count, to }, created_sprint? }` where `to` is `null` for the backlog or the target sprint id (the new sprint's id for `new-sprint`, and then `created_sprint` is that sprint). Each moved item has one History event (AC 39) attributed to the signed-in user, not to the request body. Records one `completed` sprint event holding the disposition, `done_count`, the number of items moved and the target sprint (id and name snapshot, or none for the backlog).
14. After completing, the project has no active sprint; the board shows its empty state (AC 25); another planned sprint may then be started (AC 11).
15. `GET /api/sprint-states` (in `server/routes/meta.js`) returns the ordered states with which one is initial, which is active and which is final, so the client hard-codes none.
16. `GET /api/projects/:id/sprints/next-name` returns `{ name }`: `Sprint <n>` where `n` is one more than the largest `<n>` among the project's sprint names of the form `Sprint <n>`, or `1` when there are none. The Create sprint dialog prefills it and the complete dialog defaults the new sprint's name to it; the server applies the same rule when `new_sprint_name` is omitted. 404 for an unknown project; readable on archived projects.

### Work item membership and ordering

17. `GET /api/projects/:id/issues` is unchanged in shape except that each item carries `sprint_id` and `sprint_rank` (both null for epics). It still returns all items of the project, epics included, so the Epic View, epic dropdown and swimlanes keep working. It accepts an optional `?sprint=` filter with `backlog` (non-epic items with sprint_id null), `active` (the active sprint's items) or a sprint id; other values return 400. The filter never returns epics. The Backlog page and the board use the filter or filter the full list client-side (implementer's choice), with identical results.
18. `PATCH /api/issues/:id` accepts `sprint_id` (a sprint id or null) and `sprint_rank` (integer). `sprint_id` must belong to the same project and the target sprint must not be Completed (400 for another project or unknown id, 409 for a completed sprint). A work item currently in a Completed sprint may not be moved out or edited into another sprint (409); its other fields remain editable as today. **If the item is an epic, any non-null `sprint_id` or any `sprint_rank` returns 400 `Epics cannot be added to a sprint.`** (`sprint_id: null` on an epic is accepted as a no-op.)
19. When `sprint_id` changes and no `sprint_rank` is supplied, the item is placed at the bottom of the target container. When `sprint_rank` is supplied it is the position within the target container; if two items in the container end up with the same `sprint_rank`, the container is renumbered in steps of 1000 with the moved item first among equals (same technique as `rebalanceIfNeeded`, scoped to the container, not to a status).
20. Reordering inside a container (a PATCH with only `sprint_rank`) does not change `status`, `rank` or `resolution`, and records no History event (reorders are bookkeeping, as for `rank`).
21. `POST /api/projects/:id/issues` accepts optional `sprint_id` (same validation as AC 18; omitted or null means the backlog). The item is placed at the bottom of that container and starts in the default status as today. The backlog and sprints are separate containers with separate `sprint_rank` sequences. Creating an epic with a `sprint_id` returns 400 (AC 18); an epic created without one gets null `sprint_id` and `sprint_rank`.
22. Moving an item between sprints or the backlog never changes its status, resolution, epic, assignee or comments. A done item may be dragged back to the backlog or a non-completed sprint. **Changing an item's type to an epic type** while it is in a sprint or the backlog clears its `sprint_id` and `sprint_rank` in the same save and records the sprint change in History (AC 39); if the item is in a Completed sprint the change returns 409. **Changing an epic to a non-epic type** puts it at the bottom of the backlog (it gets a `sprint_rank`); History records only the type change, since an epic had no container to move from.
23. `sprint_id` and `sprint_rank` writes need `write` (403), item exists (404), project not archived (409), then validation (400), as every other item PATCH.

### Board

24. The board of a project shows only the non-epic work items whose `sprint_id` is the active sprint's id. Items in the backlog, in planned sprints and in completed sprints do not appear in any column or swimlane. **Epic-type items are never drawn as cards in a column**, whatever the grouping. Search and filters (`docs/specs/search-and-filters.md`) apply to the visible items as before; the filter count counts visible non-epic items only.
25. When the project has no active sprint, the board shows an empty state ("No active sprint.") with a link to the Backlog page; the columns are not drawn, and the create control stays visible (AC 27). When there is an active sprint with no items, the columns are drawn empty.
26. The board header shows the active sprint's name and, when set, its goal and its dates. When the sprint is overdue (Decision 19) it also shows a visible warning banner containing the text "Overdue" and the end date, for example "Overdue: this sprint ended on 2026-10-20 (6 days ago). Complete it on the Backlog page." The banner is `role="status"`, has a link to the Backlog page, and does not rely on colour alone. No banner when no end date is set or the sprint is not yet past it.
27. Drag-and-drop between board columns and all existing item behavior work as before for the visible items. The board's create dialog and the Epic View "Create child" send the active sprint id when there is one (Decision 9), so the new item is in the sprint; for an epic type they send none. When no sprint is active the dialog shows the line from Decision 17 and the item is created in the backlog (it does not appear on the board; the dialog's success state says "Created in the Backlog" with a link to the Backlog page). Creating an epic from the board shows "Epics are not part of a sprint." instead of either line.
28. The Board and the Backlog page are linked in both directions by a project sub-navigation ("Board", "Backlog") showing the current page (`aria-current="page"`). The Backlog link is visible to every user who can open the project.
29. **Epic visibility on the board.** With Group by = Epic, a lane exists for each epic that has at least one child among the board's visible items (children in the active sprint), titled with the epic's key and title, plus the "No epic" lane. The lane header's epic key/title opens the Epic View (the existing epic chip behavior); epics with no visible child get no lane. The epic chip on a card, the Epic dropdown in the dialog and the Epic View (which lists all children of the epic, in any sprint or the backlog) all use the full project item list and are unchanged. Epics that do not fit these paths are found through the Backlog page Epics section (AC 31). The existing rule that an epic cannot be dropped into another epic's lane no longer applies on the board, because epics are not cards; its removal is not a behavior change anyone can reach.

### Backlog page

30. Each project has a Backlog page reachable from the sub-navigation (AC 28) and from the board's empty state. It lists, top to bottom: the active sprint (if any), planned sprints, then the Backlog section; then the Epics section (AC 31), the "Completed sprints" section (collapsed, each completed sprint expandable to its non-epic items, read-only) and the "Sprint history" section (AC 45).
31. The **Epics section** is read-only and collapsed by default. It lists the project's epics in key order, each row with type chip, key, title, a progress text "n of m children done" (done = terminal status, from the Epic View's data) and no drag handle, no sprint, no quick create. Clicking a row opens the epic's work item dialog (Children tab). Its empty state: "No epics." A user who can write creates epics from the board's or the dialog's create control (type Epic); the section has no create control. Epics are not counted in any sprint or backlog count.
32. Each sprint section shows its name, state badge, goal and dates when set, item count and done count, and its items in `sprint_rank` order. An overdue Active sprint also shows an "Overdue" badge with the end date (text, not colour alone). The Backlog section shows its item count and its items in `sprint_rank` order. Each row shows drag handle (writers only), type chip, key, title, epic chip, priority, status, assignee. Clicking a row opens the work item dialog (re-pointed in place, no reload). Titles, goals, sprint names and actor names are inserted as text, never HTML, and long text wraps or truncates without breaking the layout.
33. Items can be reordered inside a container by drag and drop, and dragged between containers (backlog, any non-completed sprint). A drop sends one PATCH with `sprint_id` and `sprint_rank` (AC 18-19). A drop indicator shows where the item will land; an empty container highlights as a drop target. On a server error the item snaps back and the message is shown inline. Viewers and archived projects cannot drag (rows are not draggable, no handles, no controls).
34. A quick-create row at the bottom of the Backlog and of each non-completed sprint: a title input and a Create button (Enter also submits). It creates a work item of the default type and priority in that container, at the bottom (AC 21). The input is cleared and focused for the next item; an empty or over-long title shows the validation message inline. It is hidden for Viewers and archived projects.
35. Sprint controls: a "Create sprint" button (dialog with name prefilled from AC 16, goal, start date, end date); on a Planned sprint "Start sprint", "Edit" and "Delete" (delete asks for confirmation and says its items return to the backlog); on the Active sprint "Complete sprint" and "Edit". "Start sprint" is disabled with an explanation while another sprint is active. Controls are hidden for Viewers and archived projects.
36. "Complete sprint" opens a dialog stating "N items done, M unfinished" (done = terminal status, epics not counted), with three choices: "Move unfinished items to the backlog", "Move unfinished items to <planned sprint>" (a dropdown of Planned sprints; the choice is disabled with the hint "Create a planned sprint first" when there are none) and "Create a new sprint and move unfinished items there" (with an editable name field defaulted per AC 16). The owner must choose; there is no default selected and the Complete button stays disabled until a choice is made. Confirming calls AC 12 and refreshes the page. If M is 0 the choice is not asked and the dialog only confirms completing.
37. The work item dialog gets a "Sprint" field: a dropdown with "Backlog", every Planned and Active sprint of the item's project (name and state), and the item's current sprint if it is Completed (shown and disabled, with a note that completed sprints are read-only). Changing it saves like the other fields (PATCH, AC 18), places the item at the bottom of the target (AC 19), updates the board or backlog behind the dialog without closing it and shows an error inline on failure. The field is disabled for Viewers and archived projects. For an epic-type item the field shows the fixed text "Not applicable (epics are not part of a sprint)" and is not editable; when the type dropdown is switched to an epic type in the dialog, the field changes to that text before saving.
38. A keyboard-only user can do everything drag and drop does by using the dialog's Sprint field (AC 37) and the quick-create rows.

### History and audit

39. A `sprint` field is added to `server/historyFields.js` (label "Sprint"). Changing an item's `sprint_id` by any route (dialog, drag, sprint delete, sprint complete, create with a sprint, type change to epic) records a change with old and new sprint id and name snapshots; the backlog is stored as null and displayed as "Backlog". Creating an item directly into a sprint records the usual `created` event plus no separate sprint change (the `created` event stands). History is attributed to `req.user`.
40. `sprint_rank` is not a history field (like `rank`). The history tests that require every updatable column except rank to be tracked are updated to also exempt `sprint_rank`.
41. **Sprint audit tables.** `sprint_events` (`id, project_id, sprint_id, sprint_name, kind, actor_id, actor_name, created_at, disposition, done_count, item_count, target_sprint_id, target_sprint_name`) and `sprint_event_changes` (`event_id, field, old_value, new_value`), indexed by `(project_id, id)`. As in work item history, `sprint_id`, `project_id` and `actor_id` are plain integers with no foreign key, and `sprint_name`/`actor_name` are snapshots, so events survive the deletion of the sprint and the user. Events are append-only and are never edited or deleted (not even by deleting the sprint).
42. **What is recorded** (kinds from the single-source list `server/sprintEvents.js`): `created` (AC 8, and the new sprint of AC 12), `edited` (AC 9, one change row per changed tracked field: name, goal, start date, end date; old and new values as text, empty stored as null), `started` (AC 11), `completed` (AC 13: disposition, done count, moved count, target), `deleted` (AC 10: name snapshot, items returned). The actor is always `req.user` via `actorFrom`, never the request body; the time is server time. Each event is written by `server/data/sprintHistory.js` inside the same transaction as the write it describes, so it commits or rolls back with it. Failed or refused requests (403, 404, 409, 400) record nothing.
43. `GET /api/projects/:id/sprint-history?limit=&before=` returns 200 with the project's sprint events, newest first, each with `id, kind, sprint_id, sprint_name, actor_name, created_at`, the counts and target for `completed`, `item_count` for `deleted`, and `changes` for `edited`. `limit` defaults to 50 (max 100) and `before` is an event id for paging, as for work item history. Unknown project 404, signed-out 401, readable by every signed-in user including Viewers and on archived projects.
44. `GET /api/sprint-event-kinds` (in `server/routes/meta.js`) returns the ordered event kinds with their labels and the tracked sprint fields with their labels, from `server/sprintEvents.js`, so the client hard-codes no kind or field label.
45. The Backlog page has a "Sprint history" section (collapsed by default, count shown): a read-only list, newest first, one entry per event showing the kind label, a sentence built from the event (for example "Dana Reyes completed Sprint 3: 5 done, 2 unfinished moved to Sprint 4"), and the time. Edited entries list "Field: old to new". A "Show more" button pages older events; an empty state "No sprint activity yet."; a load error with Retry. All text inserted as text. Visible to Viewers and on archived projects.
46. Sprint events created by the migration do not exist (nothing is backfilled); `Sprint 1` from the migration shows no history, only its own timestamps.

### Permissions and archived projects

47. A Viewer can `GET` sprints, the backlog, sprint history and the board data (200) and receives 403 `Your group (Viewer) is not allowed to edit work items.` on every sprint or `sprint_id`/`sprint_rank` write. Any group with `write` can do all sprint and backlog actions. The client hides or disables controls using the user's permission names from `/api/auth/me`, never a group name.
48. On an archived project every sprint write (AC 8-12) and every `sprint_id`/`sprint_rank` write returns 409 `This project is archived; its work items are read-only.` The Backlog page renders read-only. Archiving a project does not change its sprints' states.
49. A write against a sprint that belongs to a different project than the item returns 400 and changes nothing.

### Source and extensibility

50. All SQL for sprints and sprint events appears only in `server/data/` (new `server/data/sprints.js` and `server/data/sprintHistory.js`, plus the `issues` data file). Routes validate and call the data layer only.
51. No sprint state name or sprint event kind is hard-coded in `server/` outside `server/sprintStates.js` and `server/sprintEvents.js` (and the migration and index in `server/db.js`, which may import from them), or anywhere in `public/js/`. No status name and no type name is hard-coded in the new code either (epics are found through the `isEpic` flag). A source test enforces all of this, like `tests/source.test.js`.
52. An extensibility test adds a status to `statuses.js` and shows that the sprint complete counts (done versus unfinished) and the board still behave (the terminal status is still the last entry); a second adds an event kind to `sprintEvents.js` and shows it flows through `GET /api/sprint-event-kinds` unchanged.

## Data model changes

- **New table `sprints`:** `id INTEGER PRIMARY KEY, project_id INTEGER NOT NULL REFERENCES projects(id), name TEXT NOT NULL, goal TEXT NOT NULL DEFAULT '', start_date TEXT, end_date TEXT, state TEXT NOT NULL, created_at TEXT NOT NULL, started_at TEXT, completed_at TEXT`. Index on `project_id`. Partial unique index `ON sprints(project_id) WHERE state = '<active state>'` (value interpolated from `server/sprintStates.js` the way `db.js` already interpolates defaults).
- **`issues`:** add `sprint_id INTEGER REFERENCES sprints(id)` (null = backlog, and null for epics) and `sprint_rank INTEGER` (null for epics); index on `(project_id, sprint_id, sprint_rank)`. New items get `sprint_rank` from the bottom of their container.
- **New tables `sprint_events` and `sprint_event_changes`** (AC 41), created in `SCHEMA` with `IF NOT EXISTS` like the history tables. Indexes `idx_sprint_events_project ON sprint_events(project_id, id)` and `idx_sprint_event_changes_event ON sprint_event_changes(event_id)`; `sprint_event_changes.event_id` cascades with its event.
- **New single-source file `server/sprintStates.js`:** ordered list of states with flags `initial`, `active`, `final`, plus `isValidSprintState`, `initialSprintState`, `activeSprintState`, `finalSprintState`. Served by `GET /api/sprint-states`.
- **New single-source file `server/sprintEvents.js`:** `SPRINT_EVENT_KINDS` (`created, edited, started, completed, deleted`, each `{ key, label }`) and `SPRINT_HISTORY_FIELDS` (`name, goal, start_date, end_date`, each `{ key, column, label }`, in display order), the way `server/historyFields.js` lists work item fields. Served by `GET /api/sprint-event-kinds`.
- **`server/historyFields.js`:** one new entry, `sprint` with `column: 'sprint_id'` and a new kind (`sprint`: id plus name snapshot, like `issue`). `sprint_id` is added to `UPDATABLE` in `server/data/issues.js`; `sprint_rank` is added there too but not to history.
- **Migration `migrateSprints(db)`** in `server/db.js`, called from `openDb` after `SCHEMA`: idempotent, additive, per Decision 10 and AC 4-5. No existing column changes meaning; `rank` is untouched.

## Out of scope

- Estimates, story points, velocity, burndown and burnup charts, sprint reports, capacity.
- Reordering planned sprints (they order by creation), sprint templates, sprint duplication.
- Moving several items at once (multi-select, "move top N"), bulk edit, "move to top/bottom" menus.
- Filtering, searching or grouping the Backlog page (the board's filters stay as they are).
- Auto-starting or auto-completing sprints at their dates, notifications, reminders (the overdue warning is display only).
- Per-sprint WIP limits, sprint-specific statuses or columns, changing the status pipeline.
- Epic features on the Backlog page beyond the read-only Epics section (AC 31): no drag, no epic-based filtering, no creating epics there.
- Multiple active sprints, parallel boards, cross-project sprints.
- A "reopen completed sprint" action, deleting an Active or Completed sprint, editing or deleting sprint events, exporting sprint history, a per-sprint filter on the history view.
- Subtasks, rolling a sprint's goal into the board beyond the header display.
- Changing permission groups or adding a "manage sprints" permission.
